# 双读者 Spec 交付约定

这是正式 `story` 入口采用的输出与内容约定，不是实验报告。旧 `export` 入口保留双 Markdown 底稿兼容行为；`story` 使用自有生成、复核和渲染模块，不依赖开发工作区或参考项目。

## 交付边界

正式用户入口只有两份文档：

- `human-spec.html`：自包含的人读故事页，离线可读，无外部字体、图标或脚本依赖。
- `agent-spec.md`：独立可读的 Markdown 工作交接规格，可直接交给 Agent 作为上下文。
- `evidence.md` 是按需查阅的证据附件，不是第三份 Spec；与 Agent Markdown 保存在同一目录，正文不再附带证据表。

共享事实、来源、事件、生成校验报告和必要缓存是辅助材料，不是第三份用户主文档。Agent 交接只交付 Markdown，不生成或嵌入 HTML 交接页面。人读 HTML 仅用普通链接指向相邻 `agent-spec.md` 和 `evidence.md`；不添加弹窗、阅读/原文切换、复制或脚本下载按钮。交付时验证文件入口实际可取得。浏览器若不支持 Markdown，打开本地 MD 文件，不退回自制 HTML 阅读器，也不能把下载事件当作保存成功。

`_support/evidence.jsonl` 与 `_support/source.json` 是导出器建立的私有证据附件，不是原任务运行产物，不上传。对外核查使用独立 `evidence.md`；交接稿不能依赖接收方拿到私有 `_support/` 才能理解和接续任务。

七方案对比、模型评测、加法母稿、减法过程、实验说明及其脚本属于开发实验，不进入插件包、导出目录或最终用户导航。正式导出不能每次重跑七个上游方法；应使用实验后收敛的生成流程。

## 人读 HTML：让没看过会话的人理解这段工作

1. **阅读起点**：先交代背景与已有环境、真实问题、最终有效目标（Goal）、实际解决思路、本次范围、明确不做（Non-goals）、关键限制与前提，以及当前结果的验证边界，再进入故事。不用元数据或泛化摘要抢占开头；目标是希望达到的状态，不是已经达成的成果。
2. **故事与决策**：沿 target session 的因果轨迹，交代尝试、阻碍、失败后的重试、用户纠正、关键选择及理由。合并重复控制，不把失败抹成一条事后成功路径。
3. **方案怎样工作**：解释组件职责、控制流或数据流、关键参数、状态变化以及选择这些机制的原因。必要的短代码、精简日志和结构图就地解释，不全部推给 Agent 版。
4. **这次做了什么**：说明具体产物及用途、最终有效的行为约定和实质变化。交代实际观察、本次验收覆盖范围和不能外推的结论。
5. **下次怎么做**：分别考虑继续使用、再次出问题、迁移复用时的起点、检查、最小动作和停止条件。后续验收要具体，但不把已经完成的工作自动变成新待办。
6. **从这段经历带走什么**：回扣原始问题，从真实的尝试、纠正或取舍中提炼认识的变化与可迁移的判断方法，交代适用条件。不是重述摘要、增加待办或写可套在任何故事上的口号；未完成或未验证的工作不能靠结尾变成成功。

这些是内容责任，不是固定章节名字。标题和篇幅随故事调整，以自然段为主，清单只用于真正适合清单的内容。

**开头由同轮初稿生成，不是手填模板。** 它与正文、图、结尾及 Agent 交接稿共同对照完整原始事件生成，再统一复核，避免独立摘要拼接。先建立情境，再解释问题/目标与解法，最后交代必要边界；替代旧版重复的 opening/outcome 展示。建议 400–650 个可见字符，复杂多议题建议不超过 900，结构硬上限为 1400；英文、空格和标点也分别计数。不能为满足建议篇幅而截断必要信息。草稿与最终统稿分开缓存，不能把某一段以前审过当成整篇连贯。

**明确不做 ≠ 尚未完成 ≠ 尚未验证 ≠ 日志没提到。** Non-goals 只收有真人原话支持的明确排除；没有就省略整个栏目及图标，不写“未约定”等占位说明，也不留下空白列或编造排除项。scope 表达实际处理范围，不冒充用户禁令。constraints 区分用户最终有效要求与已知环境前提；结果只说实际证明到哪里。目标演变要保留起点，不把后来的方案伪装成最初要求。四轮受限补丁后仍不能通过时拒绝发布，保留上一版；证据编号与原话校验字段不进入可见概览。

**“要解决什么”不是中途故障的复盘。** 概览应先回答方案尚不存在时，用户原本面临什么困境、需要这次工作做什么。不能从“后来……”讲起，预设读者已知道先前实现；删除连接词也不足以修复内容错位。初始需求放在概览，实现后遇到的故障、观察、诊断与转向放到故事 trajectory 中。背景只交代必要情境，问题不提前倾倒排查日志；多个独立议题各自交代起点。

**整篇必须自洽。** 标题与日期范围一致，路线只保留至多 5 个关键转折，结尾不能把最后一个议题冒充整场会话的起点。多议题要交代各自主线及共同的判断方法；重复的约束和验证警告应合并而不是铺满每一节。全部断言，包括标题、路线短句、图注和结尾，都遵守正文相同的证据力度：不能用醒目短句把“局部观察”升级为“整体可靠”。没有内容的可选栏目直接不显示。

视觉表达围绕理解：用路线图帮助定位转折，用前后对照说明需求或状态变化，用“已观察／未证明”区分验证范围。不是每个 session 都必须有相同图表，也不强行填数字或图标。

**架构图是有证据条件的输出，不是必填装饰。** 先判断实际组件、职责及有方向的关系是否有足够资料，再决定画最终产物结构还是实际实现流程。标明范围和时间切片，不混画旧方案、当前方案与未来建议。每个节点、每条边都要有内部来源；区分源码/配置支持的实现约定与当次运行的实际观察，未知关系不补造。证据不足时不画图，不用通用示意图占位。图就近放在机制解释处，自包含、可离线阅读，附文字等价说明和验证边界。

**这两项必须由生成流程完成。** 生成结构化架构候选与带转折锚点的结尾，经结构检查和独立上下文语义复核后，渲染器自动布局图形并呈现自然结尾。引用和编辑锚点只供内部追踪，不变成正文编号。复核发现问题时受限重生成，仍有问题则拒绝发布新增内容；禁止用手工修改示例掩盖方法缺失。自动复核仍不是正确性保证。

正文不堆 E 编号、UUID、哈希、PID、枚举和审阅器消息。给人看不等于去技术化：保留影响理解和复用的具体错误、关键逻辑、参数单位和测试结果；重复控制、完整日志和次要兼容性细节可压缩或折叠。重要的不确定性须紧挨相关结论，用普通话解释，不能因为视觉好看就藏掉。

完整性的判断不是字数，而是读者不打开 Agent 版，也能回答：为什么做、怎么走过来、方案如何工作、留下什么、本次证明到哪里、下次怎么办。内部可以维护问题覆盖和真人输入覆盖记录，但不把这张检查表当成人读正文。

关键转折必须保留真实的纠正过程：先改错再恢复，不能写成一直正确；第一次失败后重试成功，不能只写失败；没有实测过的恢复或长期行为，不能用漂亮的成功结尾代替。

## Agent Markdown：让没参与会话的 Agent 正确接手

新发布采用 `story-output/v9`、`agent-detail/v3`、`evidence_renderer: companion/v4` 和 `agent-presentation/v2` 的 `markdown-files` 模式，旧版渲染保持兼容。证据附件明确完整源载荷仅存于导出者的私有工作区，不在交付包中，也不应默认索取；验收按任务约定的范围判断，不把每条成功工具结果一概标为“不是验收”。只有 patch 或未知参数字段的工具请求也保留有界摘录，不将未知字段误报为没有载荷；不展开成全量工具日志。旧 `companion/v1`、`companion/v2`、`companion/v3` 按原策略重算校验，呈现刷新另存新版，不重写历史文件。

`session.start.context` 作为脱敏的来源上下文保留，不算真人输入或独立执行证明。新 `human-presentation/v1` 使用中性工程会话标题，不自动宣称记录为真实执行；明确的合成/模拟历史须在两版正文保留一次来源限定。记录里使用合成测试数据不意味着会话本身是虚构的。机制复核区分取值与副作用、成功路径与清理、测试通过与对错误机制的区分力；这些模型检查仍不是正确性证明。

两版默认自然沿用源会话真人交流的语言，不向模型指定某一种目标语言，也不按自动检测结果强制翻译正文；仅在导出用户显式传入 `--language` 时才指定目标语言。提示词和旧底稿的语言不决定输出。自动检测仅用于 HTML 元数据与固定界面标签，不是正文生成约束。人读版仍是技术故事，Agent 版是可操作交接，不套用人读版的压缩预算。

`article.agent_markdown` 承载工作约定与机制地图，`article.agent_detail` 承载 resume、continuation、recipes、trajectory 和 paths；共同接受整稿复核。发布器在一级标题后插入接手起点。tool_steps 是语义步骤，不是调用列表，每步有 1–4 项 usage 摘要：真实工具、具体对象/操作和工具事件 refs；工具名必须能由所引事件核对。finding 交代实际结果与边界，decision 交代判断，不能只列工具名。完整参数/日志仍归档而不倾倒；关键失败、纠正、参数和复现入口不能因精简而消失。

引用也是交接的一部分。结构保留完整 refs；正文只保留少量“事件编号 · 角色／工具结果”短链接，指向独立 `evidence.md#e000001`。附件解释来源角色、工具/目标、短摘录和证据边界；缺失配对明确标识，助手汇报不升级为独立验证。附件与正文分别绑定发布哈希，并由同一源数据确定性重算校验，不能删除附件后静默通过。两个 MD 文件放在同一目录，在支持 Markdown 的阅读器中跟随引用，或按事件 ID 查找；纯文本浏览器不保证标题锚点跳转。MD 正文独立提供首步、预期和失配分支；交付附件仅用于核查，不作为理解前提。完整载荷仍在 `_support/`，导航摘录不是完整证据或执行脚本。

每项内容有主归属：resume 负责接手状态，工作约定负责目标和机制，continuation 负责未来分支，trajectory 负责历史过程。避免双开场、反复复制验收警告，以及最终历史阶段的 next_state 与当前接续计划冲突。缺目标层验收时，应安排有前提的补验收路线，不默认等待新投诉；真正完成的任务不制造新待办。人读故事中的后续方法集中自然收束，不机械地每章重复一套“若复发—先检查—停止条件”。

精简不等于机械截断：一个步骤保留“做什么、发现什么、为什么改变下一步”，仅当复现关键检查、识别失败或解释机制需要时才保留精确命令、参数、错误签名或短代码。通常每阶段一到三个有意义的步骤，复杂真实转折可更多。阶段开头讲触发，中间讲行动与判断，结尾讲结果和后续状态，不把相同事实在多个字段反复抄写。完整来源引用留在结构中，正文按阶段合并引用；没有记录的依据不造占位叙述。

`refresh-story` 是对已验证 v5/v6 产物的离线呈现升级：不改变已审阅 edition 或证据，不调用模型，保留原审阅回执并明确没有新一轮内容复核。新目录生成两份一致视图，报告绑定旧报告哈希；旧产物继续按旧呈现规则验证。它不能代替 `story` 对内容的新提炼与统稿。

`story --revise-from` 则是源数据绑定的内容修订：核对原始快照、解释后事件及旧稿哈希后，使用已有 edition/候选起稿，按当前完整契约重新审阅。旧审批不继承，正确内容不因反馈而无关重写；修订来源由 `draft-origin.json` 留痕。缺少工具名/请求配对时明确保留未知，不为通过校验伪造名称。接续入口先恢复当前状态；有真实外部效果的复现须写明当前授权和受控环境，诊断完成不能伪装成业务目标已验收。

交接按接收者的三种需求组织：从检查点继续当前任务；按条件调整方法以解决相似任务；必要时追溯历史为什么这么做。接续步骤具备 action/precondition/expected/otherwise 和具体验收/停止条件；复用方法具备适用条件、替换项、不变量、步骤、失败特征和验证。不能承诺脱离仓库/权限/运行态仍无缝执行；先描述缺失前提及最小恢复动作。当前用户已授权的普通改动不反复请求许可，但历史授权不自动延续到破坏性或外部操作。

每个阶段有真实触发、具体动作、工具证据、决策依据、观察结果、状态及转向。每条用户输入包括短纠正都映射到阶段；来源映射不等于语义充分性。成功、失败、放弃和未决路径按证据存在才写。决策依据是可见的、简洁的理由总结；区分记录、回顾性推断与未记录，不编造隐藏思维链。工具台账不能代替正文对关键诊断命令、失败与机制的解释。

1. **接手摘要**：当前收尾状态、首先应读什么、哪些事不要重复做。
2. **目标与原子约束**：最终有效目标、边界、用户明确要求、建议；约束逐条可独立变更，列清被替代或仍延期的要求。
3. **产物与实现上下文**：文件、入口、依赖、接口、关键参数及单位、状态转换、已有配置；历史值与当前未核实状态明确分开。
4. **Target session trajectory 与决策**：目标如何演变、尝试与结果、失败／重试／回退、为什么选择此方案、放弃了什么。
5. **这次完成与验证**：改了什么、实际测试与结果、观察证据、仅有报告的结论、未测和失效风险。
6. **下次接续计划**：按条件分支给出最小动作、前置条件、检查方式、失败后的诊断入口和停止条件；若无新任务，不发明待办。
7. **下次验收与边界**：目标条件与建议测试方法分别归因；说明验收范围、环境前提、权限／副作用和不能照搬的条件。
8. **复用方法**：适用场景、可迁移步骤、避免的误区、再次验证要求；复用的是方法，不是历史授权。
9. **未决问题与证据导航**：影响下一步的未知项、如何查证、可定位来源。未知版本／参数／测试必须写未知，不能补造。

详细不等于粘贴全部日志。优先提供能避免接班误判的信息，保留必要代码标识符与证据定位；命令只在有必要时给出，并区分历史命令、只读诊断建议和有副作用的未来操作。导出不执行它们。

Agent 版必须先有文档标题与会话末接手摘要，再展开历史轨迹。接手者应能快速找到入口、最终参数、状态初始化与寿命、环境前提和只读起手式；不能把运行中某个 PID/会话编号当作长期架构常量。涉及包装进程时，等待与退出码传播分别交代；涉及计时/状态时，明确是否跨进程持久化。疑似复发先触发核查，不自动触发卸载或删除；验收必须针对要验证的层级，不能用端口或日志代替完整功能。

## 两份文档的共同底线

两份文档共享同一事实基础，但不共享行文模板。一次是因果故事，一次是可接续工作契约。

本次验收回答“做过哪些检查，证明到哪里”；下次验收回答“继续或复用时，还需做到并证明什么”。来源引用存在不代表结论正确。争议结论应展开完整关联事件，包括失败后的重试和后续结果，不能仅凭截断片段裁决。

正式发布使用整稿 gate：同轮生成的文章、架构/结尾和概览形成一个 edition，经七维度审阅及受限补丁后再渲染，结构修复与实质审稿分别计入预算。任何组件修复都重新检查整份 edition 的引用、覆盖、章节关系及双读者一致性；未通过不替换已有文档。审阅记录和已知失败指纹留在辅助材料中，不占人读页面。自动审阅不构成事实正确性证明。

修复同时保持语言、篇幅、结构与事实约束：概览单项至多 300 字符，总计至多 1400 字符，不能靠切换语言缩短。自动模式引用少量原始真人交流片段作为语言线索，不指定目标语言，也不把历史文本当新指令。整稿复核索引包含随文工具动作、复用方法、路径说明及图注，已发现的事实问题会带入下一轮复查，避免正文修正后同义错误仍留在别处。这些索引和长度计数不是语义正确性证明，也不会自动改写事实。

阻断意见必须定位到稿件的真实 JSON 路径与原文，并引用来源原话及角色，或逐字引用实际发布契约。用户诉求类意见必须有真人输入支持，助手提出的选项不等于用户选择。纯风格建议不能阻断发布。审阅意见不满足原文/角色校验时只允许一次审阅纠正，不直接据此改坏正文；引用存在也仍不等于其逻辑充分。工具引用可自动补齐唯一调用的请求与结果，失败结果同样保留，不能因此补造执行成功。

错位引用仅在同角色的原文片段唯一匹配时自动定位；稿件路径同理。已知 Read/view 数字箭头行号可移除作为展示包装，但不折叠代码空白、不做近义匹配、不改变角色。原始审阅与定位调整分别留痕。Agent 交接稿必须给出实际可回查的 refs，不能只承诺有附件。修复器与初稿使用相同结构契约，避免猜测图节点或边枚举。

内部图节点 role 枚举不是可见文案：英文渲染时会翻译成 Entry/Control/Processing/Storage/Artifact/External。审阅不得把内部枚举当作“未翻译的正文”而改坏图。完整 brief/insights 若被模型误嵌在 article 内，只在结构无冲突且 schema 明确时确定性归位，逐字段内容不变，调整另留回执；不补造缺失对象。审阅契约变化后，旧失败意见保留为待核查线索并重新审阅，不机械应用过时裁决。

两种读者的接续步骤都要保住操作前提：保存/备份与恢复检查先于可能破坏状态的动作。下次验收须回到用户目标的层级，不以中间指标替代完整结果；“完成一次诊断”与“完成目标验收”是两种不同的停止条件。新增测试是未来建议，不是对历史已完成事项的补造。

读者审阅反馈可以作为同源、带哈希约束的待核查清单进入统稿；它不是外部事实，不能覆盖原始事件。反馈每项必须给出明确处理结果，不能因为旧模型曾返回“无问题”就忽略。新增反馈使旧审阅缓存失效，但仍复用已修好的候选，避免无关重写。开发案例的具体反馈保存在实验工作区，插件只包含通用反馈机制，不依赖案例文件。

审阅器另收 `review-focus/v2` 的确定性索引：逐字抽取标题、图标签和 Markdown 标题，接手首步、验证边界、接续条件和路径复用条件，以及概览、结尾与复用方法中的机制摘要。索引绑定当前候选哈希，不是额外证据或执行指令；完整原文仍一并审阅。用它发现短标题倒置技术属性、同稿一处要求复测而另一处擅自豁免、Human/Agent 对同一输入的接受/拒绝描述相反等矛盾。索引只帮助模型注意这些位置，不构成事实正确性证明。其版本参与审阅缓存标识。误将缺少 canonical root 事件的呈现材料作为原始输入时，在故事生成前拒绝，而不是以空历史生成文档。
