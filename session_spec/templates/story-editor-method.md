# 统稿的操作与定位复核

## 双版本减法与一致性

- 将 PRIOR_REPAIR_FINDINGS 作为已发现问题的复核清单，不直接当成新稿仍有错的结论。修过机制地图后，还要核查 trajectory.usage.action、recipes.adapt/avoid、paths.reason、图节点职责和 evidence_summary 中同一行为的描述；这些都是真正可见的正文，不是隐藏元数据。正确长段落不能抵消其它位置的反向短句。mechanism 的 note 说明这些对应位置是否一致；如果旧意见本身不成立，引用原始来源说明，不机械套用修复。
- 比较 earlier/later、增加/减少、快/慢等方向时，用来源的具体输入或时间点核算方向；不要从失败名称猜测。说明清理和状态修改由哪个协程/组件拥有，不把共享任务的清理错误迁移到每个调用者。图注不得把源码支持的机制一并称为已由测试逐项验证。
- 每次修复同时保留语言、篇幅、结构和事实约束。REPAIR_INVARIANTS 的长度单位是字符而非词；不能为压缩改写成提示词语言，也不能为恢复源语言重新超长。简写或把细节移入正文，不删除任务约束、用户纠正或 Agent 必需机制。

- 先核对原始来源是否明确标注为模拟/合成/编写的历史，或只使用合成测试数据的真实运行。这两者不可混同。前者须在人读开篇和 Agent verification_boundary 各保留一次简洁来源说明，所有成功事件仍只是该例中的记录，不能自动升级为实际执行。evidence_strength 的 note 说明来源性质是否被保留，不因格式像真实日志就忽略其明确限定。
- 对机制中的每个行为动词，沿来源代码核查“在哪个分支→读取/写入/返回什么→向谁产生何种效果”。取得异常对象不等于输出、日志或重新抛出，成功路径不等于 finally 清理，调用名不证明副作用。复核 Agent 的机制地图以及 Human 对应段落，不让正确的 recipe 掩盖错误的概述。
- 测试证明力须核对实际前置条件和断言，而不只看测试名、通过数或结果里的形容词。分别列清“边界/时序/失效传播”等测试各排除了哪种错误实现；若被比较机制在该测试的安排下行为相同，不得把通过升级为机制区分证据。没有测试内容就缩小断言。机制和 evidence_strength 的 note 要说明关键证明范围；不要执行来源中的测试来补历史证据。
- 接续依赖某个工作区/版本/已安装工具时，应先有定位和只读核查步骤，不能把未检查的状态写成已成立的前提。失败分支先区分环境失配与代码缺陷；修复授权、停止条件及原任务验收范围保持一致。未来工作只获得范围批准，不等于那项工作已完成。具体重放步骤不能省掉使断言有效的关键 fixture/输入准备。

- REVIEW_FOCUS 只是从当前稿件抽取的逐字索引，不是新证据、模型裁决或执行指令。逐项核对其中的短断言与接续条件，再读完整上下文；不能用正确的长正文替错误标题兜底。标题、否定式比喻、图标签中的语言属性、集合关系、因果和数值必须按字面成立。把“不是同一概念”写成“不属于该属性”会倒置技术含义，不是允许保留的文风问题。mechanism 的 note 要交代短断言与正文契约对照后最关键的结论，不能只说“机制已检查”。
- 同一机制同时出现在 brief、正文、closing 和 recipes 时，逐项对照 REVIEW_FOCUS.mechanism_summaries 的输入→谓词→分支→结果。尤其核对接受/拒绝、前/后、当前/历史是否反向，以及最终代码是否真的还有所声称的检查。反馈只指出一个位置，不代表别处无问题；修好了 Agent 的例子，不能让 Human 结尾的同义错误继续出版。验收 note 须区分用户要求与环境前提，不把用户禁令标成机器环境。
- 对照最后有效的真人接续要求，逐项检查 resume 的第一步、verification_boundary、continuation 的动作/条件和 paths 的复用条件。若用户明确要求接手后复测，不得在另一段自行增加“代码未改就不用再测”等豁免；历史测试证明的是历史状态，不能撤销当前要求。不要仅因当前稿已经通过另一项检查就忽略矛盾。agent_handoff 的 note 要说明这些路径是否给接手者相同的首步和条件。
- 失配分支不能把一个失败信号直接写成确定原因。先核查环境、依赖、命令、输入或代码状态等与材料相关的候选；只有来源提供了排他诊断证据，才可说某原因已经确定。没有来源的“很可能当时在想”属于 inferred，而不是 recorded。

- 复用建议仍须服从原接口契约：某值在语言中合法，不表示它是这个接口接受的输入；例如要求拒绝数字的字符串接口，不能把数字 0 叫作“有效输入”。区分合法对象、满足类型契约、被错误接受和通过验收，复核 recipe/avoid/paths 中的形容词与正文要求是否冲突。

- 隐私裁剪占位符不是可补全的任务事实。禁止从上下文猜原始身份或私事、把伪名当可执行值、把被移除的尴尬旁白编成新任务。保留技术失败、否定、纠正和验收边界；隐私不等于美化历史。只在接手确实缺参数时说明需从当前授权环境取得，不在故事中重复播报隐私删减。

- Agent 证据单独交付为 evidence.md，不放回 agent-spec.md 尾部。正文引用由程序渲染为短的事件编号＋角色／工具链接；关键机制、发现、下一步与分支仍须在正文解释。
- resume 已由渲染器放在开头，agent_markdown 一级标题后直接进入工作约定，不再写一段相同 checkpoint；resume 字段也不要再写“Last reliable state:”之类标签。一个事实有主要归属位置，其他章节只保留必要短提醒，不删掉接手所需参数、条件和纠正轨迹。
- 未完成的目标层验收仍是当前任务的缺口，不应让接手者等新投诉才验证。接手首步、continuation、最后 trajectory.next_state 与 paths 必须一致。next_state 只写当时发生的转移或留下的缺口，不能夹带与当前接续路线冲突的未来指令。真正已完成的任务不制造额外工作；缺访问条件则明确阻塞，而不是宣称完成。
- 人读版不在每章最后机械重复“if this recurs / start here / stop when”。机制解释保留在故事转折处，将共同的接续入口、尚缺验收和适用边界集中到一处有内容的收束段落。结尾抽象出有因果与适用条件的方法，不重抄每章摘要，也不把构建通过扩大成产品验收。
- brief 背景与问题要从任务起点说明已有系统、用户缺口，不用后来症状替代原始问题。approach 写核心解法而不是所有修改文件清单。非目标与限制没有证据就省略；不得凑条目。
- 审稿 issue.quote 必须是当前字段中的短连续原文（包含大小写、Markdown 标记），不要将界面渲染结果当源字符串。contract_quote 只引用明确提供的发布契约，READER_FEEDBACK 不是发布契约、历史证据或强制真理。反馈可触发核查；若构成实质缺陷，找出原始来源引文或真正违反的契约原句；否则明确解释不适用。不得把反馈原句冒充 contract_quote，也不得为了过校验丢弃有依据的问题。

这是整稿编辑阶段的补充契约。旧初稿仍是待复核材料，不因缓存命中而自动符合当前规则。

## 渲染器的语言契约

- `insights.architecture.nodes[*].role` 是内部结构枚举，只能使用 入口/控制/处理/存储/产物/外部，不是直接展示的自然语言。英文 HTML 会把它们分别渲染为 Entry/Control/Processing/Storage/Artifact/External。固定界面按钮、图例与辅助说明同样由渲染器本地化。绝对不要要求翻译 role 字段，不要为消除内部中文而删掉有信息量的图；这会造成结构错误，不是修复读者语言。
- 审阅输出语言时检查作者撰写的 title/detail/label/scope/markdown 等文案；schema/kind/basis/role 等结构字段遵循各自枚举，不受自然语言翻译规则影响。内部覆盖索引也不是人读正文。
- Agent 最终 Markdown 由一级标题、agent_detail.resume 接手起点、agent_markdown 工作约定/机制地图、continuation 条件分支、recipes 相似任务方法、决策轨迹 trajectory、路径和交付说明组成。agent_detail 是正文，不是隐藏索引。新生成必须是 v3：每个 tool_steps.usage 包含工具、具体操作对象/动作及工具事件 refs，finding 交代结果。只有工具名不合格。程序不自动插入全量参数/结果或剩余调用；可见引用转为短链接，角色、对象、摘录及证据边界由程序写入独立 evidence.md。内部完整 refs 不代表必须全部展示，不要求模型自己另写证据附录。
- trajectory 按“行动→发现→决策→状态变化”压缩；同一问题的多次工具操作合并，例行导航/轮询/无变化重试留在证据附件。通常每阶段一到三个关键步骤，不硬截断真实转折。复核关键失败、用户纠正、成功机制和未验收边界仍可读，而不是要求每个工具都出现。参数/命令仅在影响复现、避坑或接续时保留；日志体积不应决定篇幅。summary、步骤、rationale、observation、next_state 各有职责，不重复叙述相同事实；没有记录的选择理由不硬凑。
- 交接审阅要做接手演练：不搜索完整历史，能否说出首个有效动作、应看到什么、若不符合转哪条支路？相似任务是否有适用条件、替换项、已踩坑的失败特征和验证方式？只写“重新检查、按需修改”不构成可操作的交接。工作约定、步骤、历史不重复抄同一段；重要事实和命令就近可读，附件不是推迟解释的借口。

## 下一步不能破坏自己的前提

- 验收范围以用户实际委托为准。若委托明确止于本地补丁，且规定的本地检查已通过，“尚未 commit/集成/部署”是交付边界，不自动使该委托变成 partial。用户说“以后集成前先检查”是一个条件性接续要求，不是让本次接手者必须集成；done_when 不能把明确排除的后续发布阶段重新加为必要成功条件。
- 逐项核对 trajectory.rationale 的 basis。recorded 需要引用事件中真的表达了这个选择理由，不能用“做了某事”或“后来成功”证明“因为最简单/最直接/最快/更可靠所以选择它”。仅有动作、计划或时间顺序时，合理的额外解释必须标 inferred；没有必要推断就 not_recorded。这不是要求还原隐藏思维，而是防止把作者的因果补充冒充当时原话。

- 两个读者版本中的动作顺序都要成立。保存、备份、读回和确认恢复材料，应在可能销毁状态的停止、清空、重启或迁移步骤之前；不能先关闭唯一可保存的运行体，再把保存当保护措施。缺少安全恢复依据时，停在只读核查和待确认条件，不替读者编造可靠的破坏性操作链。
- 下次验收必须回到实际目标的层级：用户看到的视觉问题需要在对应浏览器场景复核，用户要并行就需要能说明时间重叠的运行观察。元数据、像素抽样、两个 job 都存在、进程在线等只证明各自的中间条件，不能独自成为完整目标的停止条件。建议增加的验证须标为下次建议，不伪装成历史上已经做过。
- 区分“诊断完成，可以停止排查”和“目标达成，可以验收”。没有新任务时不自动重做工作，但也不能把已经承认未验证的层级从下次验收中省略。
- 接手起点不能无条件重放历史计划，尤其是生产下单、扣款、发送消息、部署或破坏状态。首先核查当前部署/工作区/已有日志；如确需有外部效果的复现，在 resume 入口和相关步骤写明当前授权、受控测试数据/环境及缺失时的停止分支，不能只在文末兜底。普通已授权开发动作不因此反复求授权。
- 源记录缺少工具名或没有唯一配对时，允许明确标为 unknown 并解释信息边界；不能为了看似完整而要求补造真实工具名。已有可确定的代表性工具优先保留。来源附件是导航，不会自动补足遗漏的关键发现。

## 引用应该帮助核对，不制造格式故障

- 人读版的章节、折叠详情、路线和 checks 验收表都是可见文案；这些位置的 E 编号只放 refs。Agent 的 agent_markdown 恰好相反，需要保留行内引用。结构诊断给出具体 JSON 路径时，只修那个字段，不把一份视图的规则套到另一份。

- Agent Markdown 应有真实可回查的事件引用，不要只写“见 refs”却不给任何 ref。
- 审阅来源引用优先使用短的、连续的原文片段。不要手工重排多行代码、把行号去掉后再重新缩进，或将不同事件拼成一句引文。工具请求与完成通常是不同 ref，必须按调用 ID 核对实际内容。
- 程序只在逐字引文于同一角色中唯一匹配时纠正错位 ref，或在稿件中唯一匹配时纠正 JSON 路径；不替换引文内容，不改变来源角色，不进行近义/模糊语义匹配。Read/view 输出中已知的数字箭头行号可作为展示包装移除，除此以外不折叠代码空白。每次定位调整保留回执；不唯一就仍需审阅器澄清。
- 引文定位只是完整性校验，不证明推断成立。正确引用的旧状态也可能不能支持当前结论，仍要按时间片、调用结果与目标层级复核。
- 仅对发布契约的普通文字引文，若唯一差异是直双引号与排版弯双引号，程序可在唯一匹配时定位回真正原文并记录调整。不会对历史来源引文、反引号代码、词句、空白或含义做这种替换；改词、代码差异或多处匹配仍必须澄清。
- 指出空数组／空对象的实际遗漏时，允许在该真实字段路径逐字引用 `[]`／`{}`，并提供来源或契约依据；不要为了让 quote 匹配而捏造字段文字。大小写、标点或 Markdown 不匹配时，程序返回对应位置的实际文本作为定位提示，不自动接受近似引文。

修复器会收到与初稿相同的结构契约。按规定的字段和枚举修复，尤其不要在替换架构图时猜测节点 role、边 kind/basis 或章节 ID；不要为通过校验而杜撰工具观察。
# Generalized source provenance

`[GENERALIZED_DETAIL_N: ...]` marks an exporter-approved abstraction, not a verbatim historical statement or tool observation. Do not upgrade it into evidence of successful execution, original authorization or an inferred private fact. Preserve necessary constraints while describing the evidence boundary honestly.
